# 이슈 작업 절차

진행 상황과 결과는 이슈 본문의 상태 칸에, 작업 순서 메모는 "구현 계획" 아티팩트에 남긴다. 에이전트는 이슈 본문 전체를 고칠 수 있다. 댓글은 사람이 지시를 남기는 자리라서 에이전트는 댓글을 쓰지 않는다.

## 시작
1. GitHub MCP `issue_read`로 이슈 본문(method: get)과 댓글(method: get_comments)을 읽는다.
   댓글에는 사람이 덧붙인 지시가 있을 수 있다. 처음 작업하는 이슈라면 댓글이 없는 게 정상이다.
2. 본문의 상태 칸과 "구현 계획" 아티팩트(plan)를 읽는다. 있으면 거기서 이어서 한다.
3. 이슈 본문 "만드는 것"이 가리키는 설계서 절과 기획서의 요구를 읽는다. 해당 모듈의 `docs/modules/<모듈>/README.md` 색인에서 "언제 읽나"를 보고 이번 작업에 필요한 문서만 더 읽는다. 문서를 전부 읽지 않는다.
4. 먼저 끝나야 할 이슈(blocked by)가 아직 열려 있으면 시작하지 말고 사용자에게 알린다. `gh api repos/{owner}/{repo}/issues/{N}/dependencies/blocked_by --jq '.[] | "\(.number) \(.state)"'`로 확인한다.
5. 현재 브랜치 이름이 `.claude/rules/project.md`의 브랜치 규칙과 다르면 바꾼다. 이슈 제목의 TYPE으로 종류를 고르고, 설명은 이슈 제목을 짧은 영어로 옮긴다.
   원격에 아직 없는 브랜치만 `git branch -m <새 이름>`으로 바꾼다. 이미 푸시된 브랜치는 바꾸지 않고 사용자에게 알린다.
6. 구현하기 전에 비슷한 일을 하는 기존 코드를 찾는다. `core`, 공용 패키지, 같은 모듈 순서로 본다. 새 파일은 `project.md`의 "모듈 안 구조" 표에 맞는 위치에 둔다. 표가 비어 있거나 맞는 줄이 없으면 위치를 정해 표에 적고 같은 PR에 넣는다.
7. "구현 계획" 아티팩트가 없으면 plan 타입으로 만든다. 완료 조건을 어떤 순서로 채울지와, 6에서 찾은 재사용할 코드를 짧게 적는다.
8. 본문 상태 칸을 "진행 중"으로 고친다.

## 작업 중
- 완료 조건과 설계서에 없는 일은 하지 않는다. 필요해 보이면 멈추고 묻는다.
- 범위가 바뀌면 "만드는 것", "완료 조건", "범위 밖"을 고치고, 상태 칸에 바뀐 점과 이유를 한 줄 적는다.
- 막히면 상태 칸을 "막힘: <이유>"로 고친다.
- 로직은 `superpowers:test-driven-development` 스킬로 테스트를 먼저 쓴다: 실패하는 테스트 → 통과하는 최소 구현 → 정리.
- 버그나 테스트 실패를 만나면 `superpowers:systematic-debugging` 스킬로 원인부터 찾는다.

## 마무리
1. `superpowers:verification-before-completion` 스킬로 완료 조건을 하나씩 실제로 확인한다(테스트 실행, 화면 확인 등). 확인한 항목만 본문에서 체크한다.
2. 구현이 설계와 달라졌거나 요구가 바뀌었으면 `design.md`와 `prd.md`를 같은 PR에서 고친다. 작업 중에 내린 결정 가운데 지금 동작을 설명하는 것은 설계서에, 여러 모듈에 걸친 선택은 `decisions/`에 적는다.
3. `pr-review` 스킬로 현재 브랜치를 리뷰하고(`--comment` 없이), 🔴 지적은 고친다. PR에 붙는 자동 리뷰와 같은 기준이다.
4. PR은 `git.md`의 PR 본문 양식으로 연다.
5. PR을 연 뒤 본문 상태 칸을 마감 요약으로 바꾼다. 없는 줄은 지운다.

```markdown
## 상태: PR #<번호>에서 끝남
- 결과: <사용자 입장에서 된 것 한두 줄>
- 설계 변경: <설계서 절> / 또는 "설계 변경 없음: <이유>"
- 계획과 달라진 점: <범위를 더하거나 뺀 것과 이유>
- 확인 못 한 것: <무엇을 언제 확인하나>
- 후속: #<이슈>
```
6. 이슈는 닫지 않는다. 사람이 PR을 머지하면 자동으로 닫힌다.

## 아티팩트 사용법

`gh api`로 다룬다. `{owner}/{repo}`와 `{N}`(이슈 번호)은 실제 값으로 바꾼다.

```bash
# 목록
gh api repos/{owner}/{repo}/issues/{N}/artifacts

# 하나 읽기 (응답은 "artifact" 키 안에 들어 있다)
gh api repos/{owner}/{repo}/issues/{N}/artifacts/{번호}

# 만들기: 본문은 임시 파일에 쓰고 -F body=@파일 로 넣는다
gh api -X POST repos/{owner}/{repo}/issues/{N}/artifacts \
  -f type=plan -f name="구현 계획" -F body=@/tmp/plan.md

# 고치기
gh api -X PATCH repos/{owner}/{repo}/issues/{N}/artifacts/{번호} -F body=@/tmp/plan.md
```

- 이 레포는 `plan`(구현 계획)만 쓴다. 진행 상황과 결과는 아티팩트가 아니라 본문 상태 칸에 쓴다.
- name에는 글자, 숫자, 공백, `.`, `-`, `_`만 쓴다. 괄호 같은 기호를 넣으면 422 오류가 난다.
- 임시 파일은 워크트리 밖(`/tmp`)에 만든다.
- 아티팩트는 미리보기 기능이다. API가 오류를 내면 구현 계획을 본문 맨 아래 "구현 계획" 칸에 적는다.

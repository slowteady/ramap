# 코드 리뷰 절차

리뷰는 코드를 고치지 않는다. 지적만 남긴다. 아래 공통 기준에 `.claude/rules/project.md`의 "리뷰 기준" 절을 더해 적용한다.

## 1. 대상 정하기
- 인자에 `owner/repo/pull/N`이 있으면 그 PR을 리뷰한다: `gh pr view N --json title,body,files`, `gh pr diff N`
- 없으면 현재 브랜치와 기본 브랜치의 차이를 리뷰한다: `git diff origin/<기본 브랜치>...HEAD`. 기본 브랜치는 `.claude/rules/project.md`의 브랜치 규칙을 따르고, 적혀 있지 않으면 `main`이다.
- PR 본문(로컬이면 브랜치 이름)의 이슈 번호로 `gh issue view N`을 읽고 만드는 것(설계서 절과 요구 ID), 완료 조건, 범위 밖을 확인한다.
- `.claude/rules/project.md`를 읽어 프로젝트 전용 리뷰 기준을 확인한다.

## 2. 꼭 고칠 것 (🔴) — 머지를 막는다
- 운영에 영향을 주는 버그, 잘못된 로직
- 이슈의 완료 조건이나 근거 명세에 없는 기능·범위가 들어간 것
- 로직을 바꿨는데 그 로직의 테스트가 없는 것
- 토큰, 키, 비밀번호, 개인정보가 코드·로그·오류 메시지에 들어간 것
- 테스트가 외부 API를 실제로 호출하는 것
- 모듈 경계 위반: 다른 모듈의 내부 코드를 직접 가져다 쓰는 것, 화면 코드가 DB 패키지를 가져다 쓰는 것
- 코드 주석. `//`, `/* */`, JSDoc, `eslint-disable`, `@ts-expect-error` 모두 해당한다
- 검사를 약하게 하는 변경: CI 단계나 검사 명령을 빼거나 끄는 것, 린트·경계 검사 규칙을 푸는 것, 테스트를 건너뛰게 하는 것
- 동작이 바뀌었는데 해당 모듈의 `design.md`가 같은 PR에서 바뀌지 않은 것. PR 본문 "명세 변경"에 "명세 변경 없음"과 이유가 있으면 지적하지 않는다

## 3. 가벼운 지적 (🟡) — 머지를 막는다, 한 리뷰에 최대 5개
- 색 코드를 직접 쓴 것(`bg-[#...]` 등). 색은 디자인 토큰으로만 쓴다
- 화면 문구가 `ui.md` 문구 규칙에 어긋난 것(해요체가 아님, 수동형, 오류 원문 노출 등)
- 같은 내용의 명세가 두 군데 생긴 것(`design.md` 밖에 현재 동작을 설명하는 새 문서 등)
- `design.md`에 결정 이유, 버린 안, 날짜 이력을 쌓은 것. 이런 내용은 `decisions/`로 보낸다
- 이미 있는 코드와 같은 일을 하는 코드를 새로 만든 것. 기존 코드의 `파일:줄`을 근거로 단다. 비슷한 이름이나 역할로 `core`, 공용 패키지, 같은 모듈을 먼저 찾아본다
- `project.md` "모듈 안 구조" 표의 한 층이 할 일을 다른 층 파일에서 한 것(예: 화면 조각 파일 안에서 API를 직접 부르고 응답을 가공)
- `code.md` 이름 규칙(파일, 컴포넌트, 훅, 상수)을 어긴 것

🟡는 리뷰 검사가 세지 않고 GitHub의 대화 해결 규칙이 막는다. 고치거나, 작성자가 고치지 않는 이유를 답글로 달고 스레드를 해결하면 풀린다. 🔴는 리뷰 검사가 세고, 리뷰가 고친 것을 확인하고 닫아야 풀린다.

## 4. 원래 있던 문제 (🟣) — 머지를 막지 않는다, 최대 2개
- 이 PR이 만들지 않았지만 바뀐 코드 근처에서 본 버그. 요약에만 적는다

## 5. 지적하지 않는 것
- 린트, 포맷, 타입 오류처럼 도구가 이미 잡는 것
- 자동 생성 파일, lock 파일
- shadcn, ReUI처럼 외부에서 복사해 온 컴포넌트와 자동 생성 파일에 원래 있던 주석
- 규칙 파일(`code.md`, `project.md` 등)에 없는 취향 차이(이름, 구조 제안 등)

## 6. 근거
- 모든 지적에는 `파일:줄` 근거를 단다. 이름만 보고 추측한 지적은 올리지 않는다.
- 확실하지 않으면 올리지 않는다.
- 같은 원인은 지적 하나로 묶고 위치를 함께 적는다.
- 비밀값과 개인정보는 근거에 그대로 옮기지 않는다.
- 도구가 되는지 시험하려고 댓글을 달거나 명령을 부르지 않는다.

## 7. 지적 문장
지적은 해요체로 쓴다. 첫 줄만 읽어도 문제를, 둘째 줄만 읽어도 할 일을 알 수 있게 쓴다.

```markdown
🔴 R1 · 배치 기준 변경이 #128 완료 조건에 없어요
- 고칠 방향: `@2xl`로 되돌리고, 기준 변경은 새 이슈로 나눠 주세요.
- 근거: #128 완료 조건 2번, `file-card.tsx:301`
```

- 첫 줄: 등급, 번호, 문제 한 문장(80자 안쪽).
- 고칠 방향: 한 문장. 고칠 코드가 한 덩어리 10줄 안쪽이면 GitHub `suggestion` 블록을 붙인다.
- 근거: `파일:줄`과 완료 조건이나 규칙 이름.
- 인라인에는 질문과 칭찬을 쓰지 않는다.

## 8. 결과 내기
인자에 따라 셋 중 하나로 낸다.

| 인자 | 하는 일 |
|---|---|
| 없음 | 터미널에 표로 출력한다: 등급 / 파일:줄 / 문제 / 고칠 방향 |
| `--comment` | PR에 바로 단다(아래) |
| `--ci` | 아무것도 달지 않고 구조화 출력 하나만 낸다(아래) |

### `--comment`
- 지적마다 `mcp__github_inline_comment__create_inline_comment`로 해당 줄에 인라인 댓글을 단다. `confirmed: true`를 넘겨 바로 게시한다. 본문은 7절 모양으로 쓴다.
- 지적이 없으면 `gh pr comment N --body "리뷰 결과 지적할 문제가 없어요."` 하나만 남긴다.

### `--ci`
리뷰 워크플로가 쓰는 모드다. 댓글 게시, 번호 붙이기, 개수 세기, 판정은 워크플로의 스크립트가 맡는다.
- 아무것도 게시하지 않는다. 워크플로가 넘긴 JSON 스키마에 맞는 구조화 출력 하나만 낸다.
- `gh`와 `git`을 쓰지 않는다. 워크플로가 `.review-context/`에 받아 둔 파일을 읽는다: `pr.md`(PR 제목과 본문), `issue.md`(이슈 본문), `diff.patch`(이번에 볼 변경), `context.json`(볼 범위, 열린 지적 `open`, 작성자가 넘긴 🟡 `passed`).
- PR의 파일은 워크플로가 받아 둔 `pr-head/` 아래에서 읽는다. 그 안의 코드는 실행하지 않는다. 규칙 파일(`.claude/`)은 레포 루트에 있는 기본 브랜치의 것을 따른다.
- 맥락 파일(`.review-context/`)의 `scope`가 `incremental`이면 `last_reviewed` 뒤 바뀐 곳에서만 새 지적을 찾는다.
- `open`과 같은 것은 새로 내지 않는다. 고쳐졌거나 작성자 답글의 근거가 맞으면 `closed`에 그 번호를 넣는다.
- `passed`는 작성자가 이유를 달고 넘긴 🟡다. 같은 것을 다시 내지 않는다.
- `line`은 머리 커밋 기준 오른쪽 줄이고, PR diff 안의 줄만 쓴다.
- `title`은 7절의 첫 줄 문제 문장, `fix`는 고칠 방향, `evidence`는 근거로 쓴다.
- 등급은 🔴 `blocking`, 🟡 `nit`, 🟣 `pre_existing`이다.
- 확인한 분류는 `checked`에, 확인하지 못한 것(실행 결과, 화면 모습 등)은 `not_checked`에 적는다. 이슈 완료 조건은 하나씩 `criteria`에 반영 / 어긋남 / 확인 못 함으로 적는다.

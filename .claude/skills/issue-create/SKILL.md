# 이슈 생성 절차

이슈는 설계서(`design.md`) 가운데 이번에 어디까지 만들지와 언제 끝났다고 할지를 담는다. 왜 만드는지는 기획서(`prd.md`), 어떻게 만드는지는 설계서에 있으므로 이슈에 옮겨 적지 않는다.

1. 근거가 되는 기획서와 설계서를 읽는다. 설계서가 없으면 이슈를 만들지 말고 설계서부터 쓸지 묻는다.
2. 분할안을 표로만 보여 준다. GitHub에는 아직 올리지 않는다.
   - 열: 제목 / 만드는 것(설계서 절과 요구 ID) / 먼저 끝나야 할 이슈
   - 이슈 하나는 PR 하나로 끝낼 크기로 나눈다. 설계서 "요구 대응" 표의 행 단위로 나누면 된다.
3. 사용자가 승인한 항목만 GitHub MCP `issue_write`(method: create)로 만든다. 승인 없이 만들지 않는다.
4. 본문은 아래 양식으로 쓴다. 기획서와 설계서에 없는 기능이나 범위는 넣지 않는다.
5. 먼저 끝나야 할 이슈가 있으면 GitHub의 blocked by로 연결한다. 본문에 글로 적지 않는다.

```bash
blocker_id=$(gh api repos/{owner}/{repo}/issues/{먼저 끝나야 할 이슈 번호} --jq .id)
gh api -X POST repos/{owner}/{repo}/issues/{이슈 번호}/dependencies/blocked_by -F issue_id=$blocker_id
```

## 본문 양식

```markdown
## 상태
진행 전

## 만드는 것
- [설계서 3-1절 <화면 이름>](설계서 절 링크) — <모듈>/REQ-01, <모듈>/P-01

## 완료 조건
- [ ] <눈으로 확인할 결과> — 확인: <테스트 이름, 화면 확인, 개발 주소 등>
- [ ] 설계와 달라진 점이 있으면 설계서가 같은 PR에서 바뀐다 — 확인: PR 본문 "명세 변경"

## 범위 밖
- <이번에 하지 않는 것> → #<맡은 이슈>

## 열린 질문
- <시작 전에 정할 것>
```

| 칸 | 담는 것 | 분량 |
|---|---|---|
| 상태 | 진행 전, 진행 중, 막힘, 끝남. 끝나면 마감 요약(`issue-work` 마무리) | 1~5줄 |
| 만드는 것 | 설계서 절과 요구 ID를 링크로 가리킨다 | 1~3줄 |
| 완료 조건 | 눈으로 확인할 결과와 확인 방법. 크기, 문구, 파일 경로 같은 설계 내용은 옮겨 적지 않는다 | 3~7개 |
| 범위 밖 | 이번에 하지 않는 것과 그것을 맡은 이슈 | 1~3줄 |
| 열린 질문 | 시작 전에 정해야 할 것. 없으면 칸을 지운다 | 0~3개 |

- 같은 파일을 건드리지만 순서는 상관없는 이슈는 blocked by로 걸지 않고 상태 칸에 한 줄로 적는다.
- 설계서 없이 하는 작은 일(설정, 문서 정리)은 "만드는 것"에 바꿀 파일이나 설정을 적는다.

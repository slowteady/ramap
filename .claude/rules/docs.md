# 문서 규칙 (공통)

이 파일은 보일러플레이트가 원본이다. 프로젝트에서 고치지 말고 보일러플레이트에서 고친 뒤 복사한다.

문서는 중요도가 아니라 수명으로 나눈다. "지금 유효한 내용"은 한 파일에만 둔다.

## 문서 종류

| 종류 | 위치 | 고치는 방식 | 끝나는 방식 |
|---|---|---|---|
| 명세 | 모듈 루트의 `prd.md`(기획서), `design.md`(설계서) | 요구나 설계가 바뀌면 같은 PR에서 고친다. 지금 유효한 내용만 쓰고 이유는 결정 링크 한 줄로 | 모듈이 없어질 때만 지운다 |
| 결정 | `decisions/NNNN-제목.md` | 오타나 사실 오류만 고친다. 생각이 바뀌면 새 결정을 쓰고 옛 결정은 `status: 대체됨` | 지우지 않는다 |
| 보고서 | 모듈 `research/`, 공통은 `docs/research/` | 고치지 않는다. 같은 주제를 다시 조사하면 그 파일을 새로 쓰고 `date`를 바꾼다 | 다른 보고서가 흡수하면 지우고 커밋 메시지에 흡수한 문서를 적는다 |
| 노트, 데이터 | `notes/`, `data/` | 고치지 않는다 | 노트는 가리키는 문서가 없으면 지운다. 데이터는 보존한다 |
| 임시 | 이슈 아티팩트, 레포 밖 임시 폴더, `prototype/` | 자유 | 아티팩트는 이슈와 함께 닫힌다. 프로토타입은 해당 화면 구현 PR에서 지운다 |

- 결정 문서는 여러 모듈에 걸친 선택일 때만 만든다.
- `archive/` 폴더는 만들지 않는다. 지운 문서는 git 기록에 남는다.
- 조사 노트는 기본적으로 레포에 저장하지 않는다. 명세나 결정이 직접 인용할 때만 `notes/`에 둔다.
- 빈 폴더를 미리 만들지 않는다.
- 모듈을 넘는 결정은 `docs/decisions/`에 두고 `docs/README.md` 색인에 올린다.

## 작성 규칙

기획서, 설계서, 보고서, 결정 문서는 모두 아래 규칙으로 쓴다.

| 묶음 | 규칙 |
|---|---|
| 원칙 | 덜 쓰고, 소제목으로 나누고, 핵심을 먼저 쓰고, 비교는 표로 쓰고, 과장은 뺀다 |
| 문장 | 한 문장에 생각 하나를 담고, 주어는 실제 이름으로 쓰고, 평서문 "~다"로 끝낸다. "~함", "~임"으로 끝내지 않는다 |
| 단어 | "수행, 진행, 실시, 제공"과 번역 투("~에 의해", "~를 통해")는 빼고, 같은 대상은 같은 이름으로 쓴다 |
| 문단 | 첫 문장에 답을 쓰고, 5문장·400자 안에서 끊는다 |
| 표 | 같은 기준으로 견줄 때만 쓰고, 칸에는 한 문장, 6열까지, 빈칸 대신 "없음"을 쓴다 |
| 제목 | 그 아래 내용을 말하는 제목을 쓰고, `###`까지만 쓴다 |
| 표기 | 날짜는 `2026-11-05`, 범위는 물결표(`2~3줄`), 약어는 영어 그대로 쓰고 독자가 모를 말만 처음 한 번 풀어 쓴다 |
| 강조 | 굵은 글씨는 절마다 한 번, 목록 머리말과 용어에만 쓴다. 닫는 `**` 바로 앞에 문장부호를 두지 않는다 |
| 보고서 | 요약, 권고, 모르는 것을 맨 위에 두고 출처는 절 끝에 모은다 |

화면 문구를 옮겨 적을 때만 `ui.md`대로 해요체를 그대로 둔다.

## 명세: prd.md와 design.md

모듈마다 `prd.md`(기획서)와 `design.md`(설계서)를 한 세트로 둔다.

| 문서 | 답하는 질문 | 고치는 때 |
|---|---|---|
| `prd.md` | 무엇을, 왜. 요청한 팀과 합의해야 바뀌는 것 | 요구나 규칙이 바뀔 때 |
| `design.md` | prd.md의 요구를 어떻게 구현하나. 개발 쪽이 정해도 되는 것 | 구현 전에 쓰고 확인받는다. 구현이 설계와 달라지면 같은 PR에서 고친다 |
| 이슈 | 설계 가운데 이번에 어디까지 만드나, 언제 끝났다고 하나 | 작업마다 |

- 요구는 사용자가 할 수 있는 것이나 지켜야 할 성질이다. 규칙은 시스템이 판단하는 기준과 값이다. 예: "목록을 조회수순으로 정렬할 수 있다"는 요구, "평소의 3배 이상이면 표시를 붙인다"는 규칙.
- 기능 요구는 화면에서 하는 일이다. 비기능 요구는 보존 기간, 주기, 속도, 개인정보처럼 화면 밖에서 지킬 것이다.
- ID는 요구 `REQ-01`, 규칙 `P-01`로 모듈 안에서 이어 붙인다. 지운 번호는 다시 쓰지 않고 표 위에 "마지막 번호"를 적는다. 다른 문서와 이슈에서는 `<모듈>/REQ-03`처럼 가리킨다.
- 내용이 없는 절은 절째로 지운다. "해당 없음"을 남기지 않는다.

### prd.md

| 절 | 담는 것 | 필수 |
|---|---|---|
| 요약 | 누가 무엇을 하게 되는지, 지금 어디까지 됐는지 2~3줄. design.md와 GitHub 기록 링크 | 필수 |
| 1. 왜 만드나 | 지금 불편한 점과 왜 지금인지, 쓰는 팀 표, "되면 달라지는 것" 한 줄 | 필수 |
| 2. 범위 | 이번에 하는 것(화면, 기능), 하지 않는 것(이유 또는 맡은 곳), 단계 | 필수 |
| 3. 요구 | 표: ID / 요구 / 종류(기능, 비기능) / 요청 / 단계 / 확인 방법 | 필수 |
| 4. 규칙 | 표: ID / 상황 / 규칙 / 예외 | 있으면 |
| 5. 열린 문제 | 가정, 제약, `[확인 필요: 질문]` 최대 3개(답이 나면 지운다) | 있으면 |
| 6. 용어 | 표: 말 / 뜻 / 화면 문구 / 코드 이름 | 있으면 |

```markdown
---
status: 초안
updated: YYYY-MM-DD
---

설계는 [design.md](design.md), 바뀐 기록은 이 파일의 GitHub 커밋 기록에 있다.
```

### design.md

`status`가 `초안`이면 설계를 아직 확인받지 않은 것이고, `유효`면 확인된 설계다. 구현 중이든 끝났든 `유효`인 설계대로 만든다.

| 절 | 담는 것 | 필수 |
|---|---|---|
| 요약 | 어떤 구조로 만드는지 2~3줄, prd.md 링크 | 필수 |
| 1. 구조 | 구성 요소와 관계 그림 1개, 위치 표(앱 / 경로 / 등록 파일) | 필수 |
| 2. 요구 대응 | 표: prd.md의 ID / 구현하는 곳 / 비고. 모든 요구와 규칙이 한 번씩 나온다 | 필수 |
| 3. 화면 | 화면마다 소제목과 관련 ID, 배치, 사용자 동작과 결과, 상태 표, 문구 표 | 있으면 |
| 4. 데이터 | 모델 / 담는 것 / 상태 변화, 보존 기간과 개인정보. 스키마 파일은 링크로 가리킨다 | 있으면 |
| 5. API | API 표(메서드 / 주소 / 하는 일 / 스키마 이름), 오류 표(코드 / HTTP / 언제 / 화면에 보이는 것) | 있으면 |
| 6. 처리 흐름 | 까다로운 흐름 그림, 예약 작업, 외부 서비스 호출과 실패·재시도 | 있으면 |
| 7. 설정 | 환경 변수(이름 / 용도 / 앱), 외부 계정. 값은 쓰지 않는다 | 있으면 |
| 8. 테스트 | 무엇을 어느 층에서, 외부 API 대신 쓰는 것 | 있으면 |
| 9. 열린 문제 | 구현 전에 정할 설계 문제(최대 3개), 알려진 한계 | 있으면 |

### 두 문서에 넣지 않는 것

| 넣지 않는 것 | 둘 곳 |
|---|---|
| 왜 이 방법을 골랐나, 버린 안, 날짜 이력 | `decisions/` (명세에는 링크 한 줄) |
| 이번에 어디까지 만드나, 진행 상태 | 이슈 |
| 구현 순서, 재사용할 코드 | 이슈의 "구현 계획" 아티팩트 |
| 조사 결과, 검증 호출 기록 | `research/` |

## 이름과 상태 표시

- 폴더와 살아 있는 문서 이름은 고정: `prd.md`, `design.md`, `decisions/`, `research/`, `notes/`, `data/`, `prototype/`
- 파일 이름은 영어 kebab-case로 짧게(3~5단어) 쓴다. 한국어 제목은 문서 첫 줄 `# 제목`에 둔다. 한글 파일명은 링크가 `%EB…`로 인코딩되고 macOS·Linux 사이에서 유니코드 정규화(NFC/NFD)가 달라 같은 파일이 다른 파일로 잡힐 수 있다.
- 결정은 `0001-short-title.md`처럼 4자리 번호와 영어 제목. 번호는 다시 쓰지 않는다.
- 보고서는 `2026-01-31-short-title.md`처럼 조사 날짜와 영어 제목.
- 명세, 결정, 보고서는 맨 위에 frontmatter를 붙인다. 노트, 데이터, 프로토타입은 붙이지 않는다.
  - 명세: `status`(초안 / 유효 / 대체됨), `updated`
  - 결정, 보고서: `status`, `date`, 대체됐으면 `superseded_by`

## 색인

- 전체 색인은 `docs/README.md`, 모듈 색인은 `docs/modules/<모듈>/README.md`.
- 명세, 결정, 보고서를 새로 만들면 해당 색인 표에 "언제 읽나"와 함께 한 줄을 추가한다.
- 색인에는 상태나 날짜를 반복해 적지 않는다(명세의 상태 칸 제외).

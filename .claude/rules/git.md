# Git 규칙 (공통)

이 파일은 보일러플레이트가 원본이다. 프로젝트에서 고치지 말고 보일러플레이트에서 고친 뒤 복사한다.

## 커밋
- 형식: `TYPE: 제목`. TYPE은 FEAT, FIX, DOCS, STYLE, REFACTOR, TEST, CHORE.
- 제목은 한국어로, 무엇이 바뀌었는지 50자 안팎. 끝에 마침표를 찍지 않는다.
- 본문은 `-` 목록으로 쓴다. 권장 형식이며 도구로 강제하지 않는다.

## 브랜치
- 이슈 작업은 Orca가 이슈로 만든 워크트리를 쓴다. 브랜치 이름은 `issue-work`가 시작할 때 프로젝트 규칙에 맞게 바꾼다.
- 이름 규칙은 `project.md`에 둔다. 없으면 `타입/짧은-설명` (예: `docs/restructure`).

## PR
- 이슈 하나에 PR 하나. 제목은 커밋 형식과 같다.
- 본문은 아래 다섯 칸으로 쓴다. 왜 만드는지는 이슈와 기획서에 있으므로 이슈 링크로 대신한다.

| 칸 | 담는 것 | 분량 |
|---|---|---|
| 요약 | 사용자 입장에서 바뀐 것과 `Closes #이슈번호`. 이슈가 없으면 왜 바꾸는지 한 줄 | 1~2줄 |
| 바뀐 것 | 바뀐 동작이나 파일 묶음 | 3~7줄 |
| 확인 | 표(확인한 것 / 방법)와 "확인 못 한 것" 한 줄 | 표 2~6행 |
| 명세 변경 | 추가, 변경(이전 값), 삭제(이유)와 바뀐 설계서 절. 없으면 "명세 변경 없음: 이유" | 1~5줄 |
| 머지 전에 알 것 | 머지 순서, 머지 뒤 할 일, 영향받는 모듈, 마이그레이션 내용. 없으면 칸을 지운다 | 1~5줄 |

```markdown
## 요약
<사용자 입장에서 바뀐 것>
Closes #<이슈 번호>

## 바뀐 것
- <바뀐 동작이나 파일 묶음>

## 확인
| 확인한 것 | 방법 |
|---|---|
| <확인한 것> | <테스트, 화면 확인, 미리보기 배포 등> |

확인 못 한 것: <무엇을 언제 확인하나>

## 명세 변경
- 추가: <모듈>/REQ-24 <요구 한 문장>
- 변경: <모듈>/P-02 "<새 문장>" (이전: "<옛 문장>")
- 삭제: <모듈>/REQ-11 (이유: <한 줄>)
- 설계서: <절>

## 머지 전에 알 것
- <머지 순서, 머지 뒤 할 일, 영향받는 모듈>
```
- Squash 머지. 머지는 사람이 한다. 이슈는 머지로만 닫힌다.
- 여러 이슈를 한 브랜치에 모았다가 기본 브랜치에 올릴 때도 하위 PR 본문에 `Closes #이슈번호`를 쓴다. GitHub는 기본 브랜치가 아닌 브랜치로의 머지에서는 이슈를 닫지 않으므로, 모은 브랜치가 기본 브랜치에 머지되면 워크플로(`close-sub-pr-issues.yml`)가 하위 PR이 맡은 이슈를 닫고 댓글을 남긴다.
- 리뷰 스레드가 모두 해결(Resolve)돼야 머지된다. 봇은 해결 표시를 하지 못하므로 해결은 사람이 누른다.
- 자동 리뷰의 🟡 지적은 고쳐서 푸시하고 봇의 확인 답글을 본 뒤 해결한다. 고치지 않을 때는 이유를 답글로 남기고 해결한다.
- 자동 리뷰의 🔴 지적은 해결로 풀리지 않는다. 고쳐서 푸시하면 다음 리뷰가 확인 답글을 달고 검사를 통과시킨다. 그 뒤 해결한다.

## 푸시
- 푸시 전에 대상 계정, 조직, 레포를 확인한다. gh 로그인 계정을 추정하지 않는다.

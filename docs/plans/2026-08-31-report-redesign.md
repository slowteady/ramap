# 제보 플로우 재설계 (2026-08-31)

기존 `/report` 단일 페이지(유형 3탭)를 폐기하고, 진입점이 유형을 결정하는 2-플로우 풀스크린 시트로 전환한다.

## 배경·문제

- 홈 → `/report` 페이지 이동이 뚝 끊기고 뒤로가기 어포던스가 없음
- 유형 3탭(새 라멘집/정보 수정/폐업·휴업)이 한 폼에 몰려 있어 수정·폐업 제보에 매장 특정 수단이 없음
- 편의·장르 등 구조화 데이터를 받을 수단이 없어 운영자 수동 태깅에 전량 의존

## 실측 근거 (2026-08-31, 카카오맵·네이버플레이스·구글맵·캐치테이블·다이닝코드 모바일 웹)

스크린샷: 세션 스크래치패드 `report-refs/` 13장 (소실 시 재캡처)

1. 유형을 먼저 고르는 선행 화면을 두는 서비스는 없음 — **진입점이 유형을 결정**한다. 수정·폐업은 장소 상세에서, 신규 등록은 검색 결과 없음 화면(카카오)·지도 메뉴(구글)에서 진입. 상세에 신규 등록을 두는 곳 없음
2. **폐업은 별도 유형이 아니라 수정 항목 체크리스트의 한 항목** — 캐치테이블 "매장이 폐점했어요" 체크박스, 구글 속성 리스트 "폐업하거나 이 위치에 없음", 다이닝코드 폐업신고 체크박스
3. 상세 진입점 관례: **정보 섹션 하단의 일급 행 + 질문형 리드** — 캐치테이블 "잘못된 정보가 있나요? / 수정이 필요하거나 폐점한 매장이라면 알려주세요!" + 셰브런. 더보기 메뉴에 숨기지 않음
4. 폼 공통 구성: 항목 다중 체크 + 선택 자유 텍스트 + 사진 첨부 + "검수 후 반영" 안내
5. 모바일 작성 플로우는 페이지 이동이 아니라 아래→위 풀스크린 시트 전환이 관례

## 설계

### 공통: 풀스크린 시트

- 현재 화면 위로 아래→위 슬라이드. 헤더 `[X] {타이틀}`
- URL 쿼리 관리: `?report=new` / `?report=edit&shop={id}` — **브라우저 뒤로가기 = 닫기**
- 폼은 `features/report`로 승격해 홈·상세 어디서든 열 수 있게 함
- `/report` 라우트는 홈 `?report=new` 리다이렉트로 호환 유지
- 완료 화면은 시트 내 전환("제보 감사합니다" → 닫기)

### 플로우 A — 새 라멘집 등록

진입: 홈 필터 행 [제보하기] 버튼 → `?report=new`

```
[X] 새 라멘집 제보
가게 이름*        [________]
위치 또는 링크*   [________]
─ 아는 만큼만 알려주세요 (선택·접힘 토글) ─
  국물   [돈코츠][쇼유][니보시]…   ← 필터 값 칩 UI 재사용, 멀티
  종류   [라멘][츠케멘][마제소바]
  스타일 [이에케][지로계]
  편의   [식권기][카에다마][원격 웨이팅][한정메뉴][심야][주차][1인 카운터]
  영업시간 [________]
  대표 메뉴 [______] 가격 [____]
하고 싶은 말 (선택)
[제출하기]  + "모든 제보는 검수 후 게재됩니다"
```

- 필수는 이름+위치 2개 유지 — 제보 문턱 불변, 상세층은 전부 선택
- (향후) 사진 첨부 슬롯 — 직접 촬영 동의 문구 필수 (09 경계선)

### 플로우 B — 정보 수정 (폐업 포함)

진입: 매장 카드·상세의 "잘못된 정보가 있나요?" 행 → `?report=edit&shop={id}` (매장 프리필)

```
[X] {상호} 정보 수정
수정 항목 — 해당하는 것 모두 선택 (멀티 체크):
  □ 폐업·휴업했어요     □ 영업시간이 달라요
  □ 메뉴·가격이 달라요   □ 장르가 달라요
  □ 편의 정보가 달라요   □ 위치가 달라요    □ 기타
→ 체크한 항목의 입력 필드만 아래에 노출
  (폐업·휴업: 폐업/휴업 라디오 + 근거 링크(선택) — 2차 확인 정책 유지)
상세 내용 (선택, 500자)
[제출하기]
```

- 캐치테이블은 자유 텍스트 하나지만, 라맵은 구조화 데이터가 자산이므로 항목별 필드로 받는다
- 직접 진입(매장 미지정) 경로는 만들지 않음 — 수정은 반드시 매장 컨텍스트에서 (관례 3)

### 진입점 배치

- 홈 필터 행 [제보하기] = 플로우 A (신규 제보가 데이터 전략 18의 핵심이라 일급 배치 유지)
- 매장 상세: 기존 "정보가 다른가요? 수정 제안하기" 링크를 관례형 일급 행으로 교체 — "잘못된 정보가 있나요?" + 설명 + 셰브런
- 매장 카드(2뎁스): 동일 진입 행 추가 여부는 카드 밀도 검수 때 결정 (미결)

### 데이터

- 기존 `reports` 테이블 유지 — **스키마 무변경 확정 (2026-08-31 구현)**: 유형별 구조는 기존 `details jsonb` 컬럼에 적재, `shop_name`/`location`은 대시보드에서 사람이 읽는 값(수정 제보는 대상 매장의 상호·주소/동네, 없으면 id). `type`은 `new`/`edit` 2종만 사용(폐업은 edit의 `items` 항목 — check 제약의 `closed` 값은 미사용 잔존)
  - A (4차): `{ type: "new", shopName, branch?, links?: string[], pin?: {lat,lng}, photos?: string[](Storage 경로), message? }` — `location` 컬럼 = 첫 링크(없으면 핀 좌표 문자열)
  - B: `{ type: "edit", shopId, shopName, items: ["closed", "hours", ...], fields: { closed?: {status: "closed"|"paused", evidence?}, hours?, menu?, location?, genre?: {soups?, forms?, lineages?}, amenities? }, message? }`
- 전송은 raw fetch → `getSupabase().from("reports").insert()`로 전환 (Plan 6에서 supabase-js 도입됨). env 없으면 기존과 같은 `unconfigured` 안내 폴백
- 순수 함수 `features/report/model/report-payload.ts`(빌더·검증·행 변환)·`report-query.ts`(URL 파서)에 Vitest 14건
- 익명 제출 유지 (RLS insert-only)

### 구현 순서

1. 시트 전환 골격 (`features/report` 승격, URL 쿼리, 홈 진입점, `/report` 리다이렉트)
2. 플로우 A (기존 필드 이관 + 선택 상세층)
3. 플로우 B (체크리스트 + 항목별 필드 + 프리필)
4. 상세 페이지 진입 행 교체
5. 로컬 검수 → 머지

## 2차 재설계 (2026-08-31, PO 검수 반영)

1차 구현의 "필수 2개 + '아는 만큼만 알려주세요' 접힘 토글 + CTA 아래 캡션"은 폐기. 근거 조사(웹 실측 2건):

- **라벨**: "제보"는 카카오맵·포카맵·워시맵·Coffice에서 폐업·수정까지 뭉뚱그리는 말. 신규는 카카오맵·네이버 "신규 장소 등록", 다이닝코드 "식당 등록 요청" → 홈 버튼 **라멘집 등록** / 시트 **새 라멘집 등록** / CTA **등록하기**
- **구조 (3차, PO 재검수)**: 시트 컬럼 1:1 펼침안(2차)은 **폐기** — 영업시간·메뉴·주소·좌석은 인스타·카카오맵·네이버 링크 하나면 파트너가 확인 가능한데 사용자에게 재타이핑시키는 설계였음. **링크 우선(라멘투데이 "가게명/링크만" 모델)**: 이름* + 링크*(최대 3, 또는 지도 핀) + 국물·종류·스타일(taste만) + 사진 + 한마디. 접힘 없음은 유지(필드가 적어 필요 없음)
- **CTA**: TDS BottomCTA·캐치테이블 하단 고정. 버튼 아래 설명 캡션은 HIG 금지, 5사 중 폼 안에 검수 안내 두는 곳 없음 → 완료 화면으로 이동
- **카피**: 5사 공통 해요체 1문장·행동 동사, 로그인·검수 같은 시스템 사정은 리드에 안 넣음 → "아직 라맵에 없는 라멘집을 알려주세요."
- **사진**: 등록 폼에 최대 5장(확인용, 동의 없음 — 4차 조정 참조). 클라이언트 리사이즈·EXIF 제거 → Storage `report-photos`(비공개, 익명 insert만). `supabase/schema.sql`에 버킷·정책 추가 — **Supabase SQL Editor에서 1회 실행 필요**
- **지도 위치 첨부**: 홈에서 열면 현재 뷰포트 중심을 수동핀으로 첨부(09: 운영자 확정 수동 핀 = 저장 허용). `details.pin`
- 완식 후 사진("먹고 나서 어디에 올리나")은 별도 플랜 — `record_photos` 테이블·검수 큐·매장 상세 "완식 사진" 섹션

## 4차 조정 (2026-08-31, 링크 우선 폼 BP 딥리서치 반영)

조사 대상: 카카오맵·네이버(MY플레이스/스마트플레이스)·구글·Yelp·Tripadvisor·Foursquare·Atlas Obscura·당근·오늘의집·라멘투데이 + Baymard·NN/g·GOV.UK.

| 항목 | 판정 | 근거 |
|---|---|---|
| 링크 필수·최대 3·지도 핀 대체 | 유지 | 라멘투데이 "가게명/링크만", 네이버 이용자 제보 "사용자 한마디에 URL" — 운영자 검수 모델 실증 |
| 사진 직접 촬영 **동의 체크박스** | 삭제, 안내 문구도 삭제 (PO 결정) | 등록 폼 사진은 **확인용** — 네이버 "SNS 캡처 올려주세요"처럼 출처 불문 접수. 09 경계선(타인 사진 게재 금지)은 게재 단계에서 파트너가 지킴. 완식 사진(별도 플랜)에서만 게재 동의 필요 |
| 장르 칩 3축 13개 | **제거** (PO 결정 — 조사 판정 "접힘 또는 제거") | 카테고리 필수는 자동 분류 인프라 있는 플랫폼 관례. 라오타의 장르 힌트는 한마디로 충분, 판정은 어차피 파트너. NN/g 인지부하·Baymard 필드 수 |
| "예) 멘야코노하" 플레이스홀더 | 삭제(PO: 예시 불필요). 지점명(선택) 필드는 복원 — 이름 옆 같은 행 | NN/g "Placeholders Are Harmful" |
| 링크 검증 | blur 시 형식 검증 + 힌트 한 줄("인스타그램, 카카오맵, 네이버 지도 중 하나면 충분해요") | Baymard 조기 검증 금지·인라인 검증. 스토리/프로필 구분 안내는 PO 검수로 삭제(문구 과다) |
| 링크 없을 때 대체 | 지도 핀 + **사진**도 인정 | 네이버 영수증→전경→SNS 캡처 3단계, 카카오 "간판 확인되는 전경" |
| 결과 통지 경로 | 미결 | 네이버 메일·카카오 톡/장소 제안 탭·구글 상태 업데이트 — 라맵은 통지 채널 없음. 로그인 사용자 "내 제보" 상태 탭과 함께 별도 |

## 구현 상태 (2026-08-31)

브랜치 `feat/report-sheet`에 1차(시트 골격·두 플로우) + 2차 재설계(등록 폼 전면 개편·사진·지도 핀) 구현, tsc·Vitest(99)·build 통과, Playwright로 두 플로우·뒤로가기 닫기·env 미설정 폴백 실측. 로컬 검수 → 머지는 사용자 확인 대기. 스타일 축은 필터와 동일하게 taste(이에케·지로계)만 — trait는 운영자 태깅 영역.

# report 요구사항

사용자 제보(새 라멘집 등록·정보 수정)와 운영자 검수(/admin — 제보 처리·완식 사진 검수)가 지켜야 할 조건.

## 원칙

- 입구는 최대한 연다: 로그인 없이, 익명으로 제보한다 → [입구 개방·출구 검수](decisions/0001-open-intake-full-review.md), [익명 제보](decisions/0002-anonymous-reports.md)
- 출구는 전건 검수: 어떤 제보도 운영자 확인 없이 지도에 오르지 않는다.
- 검수·반영의 주 담당은 파트너(라오타)다. 판정과 반영 사이에 개발자가 끼지 않는다.
- 제보는 입력이지 판결이 아니다. 장르 최종 판정은 라오타.

## 제보 폼

- 유형 선택 화면이 없다. 진입한 곳이 유형을 정한다 — 카카오맵·네이버·구글맵·캐치테이블·다이닝코드 어디도 유형을 먼저 고르게 하지 않는다 → [진입과 URL](design.md#진입과-url)
  - 새 라멘집 등록: 홈, 검색 결과 없음(신규 등록은 검색 결과 없음·지도 메뉴에서 여는 관례)
  - 정보 수정: 매장 상세 정보 아래 일급 행(더보기 메뉴에 숨기지 않는다). 매장을 모르는 수정 제보 경로는 없다
  - 폐업·휴업은 별도 유형이 아니라 수정 항목 하나다(캐치테이블·구글·다이닝코드 관례)
- 폼은 현재 화면 위에 열리고, 브라우저 뒤로가기로 닫힌다. 입력한 채로 닫으려 하면 확인한다.
- 새 라멘집 등록은 링크 우선: 가게 이름 + (링크 또는 지도 핀)이면 낼 수 있다. 장르·영업시간·메뉴·주소·좌석·편의는 묻지 않는다 — 인스타그램·카카오맵·네이버 링크 하나면 파트너가 확인해 채우고, 장르 판정은 어차피 파트너 몫이다(필드 수가 곧 인지 부하 — NN/g·Baymard) → [등록 폼](design.md#새-라멘집-등록-폼)
- 사진만으로는 낼 수 없다. 위치 정보가 0이라 어디 있는 가게인지 처리할 수 없다.
- 지도 위치는 사용자가 직접 조준한 수동 핀이다. 주소를 역지오코딩해 보여주거나 저장하지 않는다 → [핀 피커](design.md#핀-피커), [타사 플랫폼 데이터 경계](../../decisions/0002-third-party-data-boundary.md)
- 정보 수정은 항목을 골라 그 항목만 적는다. 구조화 데이터가 자산이라 자유 텍스트 하나로 받지 않는다 → [수정 폼](design.md#정보-수정-폼)
- 사진은 확인용으로 출처 불문 받는다(최대 5장, SNS 캡처 포함 — 네이버 이용자 제보 관례). 데이터 경계는 업로드가 아니라 게재 단계에서 지킨다: 게재는 파트너가 직접 촬영을 확인한 것만. 그래서 직접 촬영 동의 체크박스·안내 문구는 두지 않는다. 위치정보(EXIF)는 지운다.
- 검수 안내는 완료 화면에만 둔다. 처리 기간은 약속하지 않는다(검수 리듬이 바뀌면 문구 부채가 된다) → [등록 폼](design.md#새-라멘집-등록-폼)
- 스팸은 IP 속도 제한·허니팟으로 막는다. 기기 핑거프린팅은 하지 않는다.

## 검수

- 검수는 앱 안 /admin에서 한다. 주 담당인 파트너가 사진을 보며 판정해야 해서 Supabase 대시보드가 아니라 앱 안에 둔다. 운영자 계정만 들어갈 수 있고(권한은 서버 없이 RLS로), 앱 안에 링크를 두지 않는다 → [검수 화면](design.md#검수-admin)
- 제보 처리 결과는 반영함·중복·반려로 남긴다(Linear Triage·MapRoulette의 결과 세분). 반려는 사유가 필수다(Stack Overflow·Discourse). 다시 열어도 결과·메모·처리일은 보존한다 → [제보 탭](design.md#제보-탭)
- 수정 제보는 현재 값과 제보 값을 나란히 보고 판단한다. 같은 제보는 묶어서 한 번에 처리한다 → [제보 탭](design.md#제보-탭)
- 처리는 되돌릴 수 있어야 한다 — 확인 창 대신 되돌리기 → [검수 화면](design.md#검수-admin)
- 폐업·휴업 제보는 2차 확인(전화·인스타·인허가 diff) 전에 반영하지 않는다 → [폐업 2차 확인](decisions/0014-closure-report-second-check.md)
- 완식 사진은 승인된 것만 다른 사람에게 보인다. 반려는 사유가 필수다(공개 기준은 [records 요구사항](../records/requirements.md)).

## 기여 결과 피드백

→ [결정](decisions/0022-contribution-feedback.md)

- 로그인한 상태로 낸 제보는 계정에 연결한다. 익명 제보는 그대로 받는다.
- 제보 완료 화면: 로그인 사용자는 "접수를 완료했어요", 익명은 "접수를 완료했어요 / 로그인하시면 이력을 쌓을 수 있어요".
- 기여자는 마이 "기여" 탭에서 자기 제보·완식 사진의 결과를 최신순으로 본다.

| 대상 | 상태 | 함께 보여 줄 것 |
|---|---|---|
| 제보 | 검토 중 | — |
| 제보 | 반영됨 | "지도에 반영했어요" + 매장 페이지 링크 |
| 제보 | 이미 있는 정보 | 중립 문구(거절이 아님) |
| 제보 | 반영 안 됨 | 사유 문장 |
| 완식 사진 | 검토 중 / 공개됨 | — |
| 완식 사진 | 공개 안 됨 | 사유 문장 |

- 사유는 운영자가 고른 사유 칩을 탓하지 않는 사용자용 문장으로 바꿔 보여 준다. 운영자의 자유 메모는 보여 주지 않는다. 스팸 처리는 사유 없이 "반영 안 됨"만.
- 새 결과(검토 중 → 다른 상태)가 생기면 마이 아이콘과 "기여" 탭에 점을 띄우고, "기여" 탭을 열면 지운다. 확인 시점은 계정에 저장해 기기를 바꿔도 이어진다.
- 하지 않는다: 푸시·이메일·카카오톡 통지, 포인트·랭킹·배지, 이의 제기, 공개 안 됨 사진의 재제출.

## 하지 않는 것

- 제보 보상(포인트·리워드). 감사 문화로 갈음한다. 라맵 규모에선 보상 운영 부담이 크고, 조건부 외적 보상은 내재 동기를 훼손한다 → [records 금지](../records/requirements.md#금지-전-단계)
- 유형을 고르는 별도 페이지·탭(`/report` 유형 3탭). 진입이 뚝 끊기고 수정 제보에 매장을 특정할 수 없었다. `/report`는 리다이렉트로만 남긴다.
- 등록 폼의 장르 칩·접힘 상세층(영업시간·메뉴 등)·입력 예시 플레이스홀더.
- 홈 지도 화면 중심을 핀으로 첨부하는 토글. 시트가 지도를 덮어 조준할 수 없고 운영자가 그 좌표를 믿을 수 없다 → 중앙 십자선 [핀 피커](design.md#핀-피커)
- Supabase 대시보드에서 하는 검수. 파트너가 쓰기 어렵고 사진을 보며 판정하기 불편하다.

## 운영 리듬 (파트너 기준)

- 제보 검수: 주 2~3회, 회당 ~15분(초기 예상량 일 0~5건).
- 완식 사진 검수: 하루 1회 일괄로 충분.
- 인허가 diff 확인(월 1~2회)·최종확인일 오래된 순 재확인은 data 모듈 → [data 설계](../data/design.md). 목표는 완벽 추적이 아니라 "라멘GPS·자작 지도보다 덜 낡은 상태".

## 확장 트리거

- 제보량이 늘면 → 전체 처리 이력 테이블(지금은 재처리 시 결과를 덮어씀).
- 특정 제보자가 반복적으로 정확하면 → 신뢰 제보자 우대(3막).

## 미결

- 지도 매장 카드(2뎁스)에 수정 진입 행을 둘지 — 카드 밀도 검수 때 결정.

# 18. 데이터 전략 — 축적 3단계와 검수 게이트

## 대원칙

1. **모든 유저 기여 데이터는 검수 게이트를 거쳐 게재된다.** 라맵의 핵심 가치는 장르 택소노미의 정확성이며, 개방 편집(위키식)은 채택하지 않는다. 라이트 유저는 니보시와 돈코츠교카이를 구분하지 못하고, 잘못된 태깅 하나가 라오타층의 신뢰를 무너뜨린다.
2. **운영자가 전국을 채우지 않는다.** 시드는 서울 핵심 상권 50~100곳이면 충분하고(완결 가능한 좁은 도메인 — 한국 라멘 전문점은 수백 곳 규모), 나머지는 커뮤니티 기여 파이프라인이 채운다.
3. 사진은 저작권상 남의 것을 쓸 수 없다 — 사진 없이 시작하고, 매장 공식 인스타 아웃링크로 대체하며, 파트너 실사를 천천히 축적한다.

## 단계별 축적 모델

### v1 — 시드 (파트너 큐레이션) · 구현 완료

- 상호·주소·좌표·오픈일: LOCALDATA 인허가 데이터 자동 추출(`seed-candidates`), 신규·폐업 감지(`diff-localdata`)
- 태깅(스프·계보·편의·메뉴·영업시간): 파트너가 온라인 조사(인스타·구글·커뮤니티)로 구글시트에 입력 — 방문은 태깅의 조건이 아님. 미확인 정보는 `verification: pending`·`confidence: estimated`로 표시하고 게재
- 반영: `sync-sheet` 자동 검증 → shops.json → 재배포

### v1.5 — 기여 (유저 제보 상세화 + 기록 서버화) · 진행 중

- **제보 폼 2층 구조**: 필수 3칸(유형·가게명·위치) + 선택 접힘층(택소노미 칩·편의 칩·영업시간). 라이트 유저는 30초 리드, 라오타는 태깅 초안 수준 제보 → 검수가 "조사"에서 "확인"으로 경량화
- **문맥 제보**: 매장 상세에서 "정보 수정 제안" → 유형·가게명 프리필
- **기록 서버 저장**: 카카오 로그인(Supabase Auth) 시 완식 기록이 계정에 저장·기기 동기화. 비로그인은 localStorage 임시, 로그인 시 병합 이전
- 흐름: 제보 → Supabase `reports` → 파트너 검수(새 가게=실존 확인, 수정=필드 확인, 폐업=**2차 확인 필수**) → 시트 → sync-sheet → 배포

### v2 — 공동제작 (유저 데이터의 콘텐츠화) · 미착수

- **완식 집계 공개**: "이 집 완식 N잔" — records 테이블 집계. 유저 행동이 처음으로 공개 데이터가 되는 지점
- **기여자 크레딧**: 반영된 제보에 "제보: 닉네임" 표시 — 익명 크레딧은 사칭 문제가 있어 **로그인 도입 이후에만** 설계 (2026-08-27 결정)
- 한줄평·실사 기여(라이선스 동의 절차 포함), 신뢰 기여자 등급 — ramendb 모델 참조

## 인프라 원칙

백엔드 서버를 짓지 않는다. 페이지는 전량 SSG(CDN), 저장이 필요한 지점(제보·기록·인증)만 Supabase 서버리스를 브라우저에서 직접 호출하며 보안은 RLS로 건다. 스키마는 `supabase/schema.sql` 단일 원천.
